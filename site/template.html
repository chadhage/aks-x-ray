AKS CONFIGURATION ASSESSMENT

Get started with AKS X-Ray

Check cluster configuration against selected Microsoft recommendations. Results list configuration differences, collection errors, and checks that require manual review.

Collect read-only evidence locally, then open your results. This page does not sign in, connect to Azure or Kubernetes, or run commands.

01 / PREREQUISITES

Prepare your tools and access

  • Install Node.js 22+, Git, Azure CLI and a compatible kubectl. No npm dependencies are required. Entra-authenticated contexts may also need kubelogin.
  • Use your organization's normal process to sign in to Azure and prepare an existing Kubernetes context for the intended cluster.
  • Obtain approved Azure metadata read access and Kubernetes get/list access for the selected checks. Missing permissions remain explicit evidence gaps.

Review permissions and prerequisites

Clone the repository and identify your target

git clone https://github.com/chadhage/aks-x-ray.git

Keep the target subscription GUID, resource group, cluster name and context ready. The collector never chooses a subscription, downloads credentials or switches context for you.

INTERPRET AND PROTECT

        
Result limits and data handling

        
    
          
  • Review collection errors, unknown results, timestamps and target binding before drawing conclusions. Manual reviews and tests not run are not passes.
    • 
          
  • The pass rate covers evaluated pass/fail controls only. Neither it nor evidence coverage measures overall health, security or compliance.
    • 
          
  • Reports contain sensitive resource names, endpoints and identity metadata. Keep your output private; never publish real cluster reports to the public website.

RESULT STATUS
Result definitions

          

            
Pass
The specific assertion is supported by observed configuration or a recorded synthetic measurement. It does not establish compliance for the cluster.

            
Fail
Observed evidence contradicts the stated recommendation or exposes a configuration conflict. Review workload context and approved exceptions before remediation.

            
Review
Owner intent, telemetry, physical infrastructure, policy assignments or operational evidence is required. Review is never counted as pass.

            
Unknown / error
Required access, API fields or valid measurements are missing, or evaluation failed. Unavailable data is never replaced with an empty successful result.

            
Not applicable / not run
Platform/profile excludes a control, or the user did not authorize an active test. Neither is successful evidence.

          

        

        

          
COLLECTION AND TEST BOUNDARIES
Read-only collection by default

          
    
            
  • Default collection uses Azure read operations and Kubernetes get/list only. No login, credential download, context switch, secret reads, exec or apply.
    • 
            
  • Inventory is projected before persistence. Secret values, kubeconfig credentials, environment values, application logs, commands, arbitrary annotations and event messages are not exported.
    • 
            
  • Reports still contain sensitive resource names, labels, endpoints, RBAC subjects and subscription metadata. Protect them and review before sharing.
    • 
            
  • Active tests require explicit authorization, a confirmed context and a verified target. Only owned synthetic resources are created and cleaned up.
    • 
            
  • The HTTP load test runs within fixed request and duration limits. It does not measure application capacity or sustained load. Admission testing submits a server-side dry-run; it does not attempt exploitation.
    • 
            
  • Backups, failover, host security, Azure Local physical fault domains, external ingress/WAF, full effective routing, CVEs and identity governance need additional evidence.
    • 
          

        

      

      

        
RESULT METRICS
Observed configuration and evidence coverage

        
The pass rate is pass / (pass + fail) and is suppressed when target binding is unverified. Evidence coverage is complete pass/fail controls / all applicable controls, including manual reviews and not-run tests. Neither metric represents overall cluster health. The production profile is the default; apply recommendations in the context of the workload, platform, and documented design decisions.

        
Collection is not an atomic snapshot: each source carries its own timestamp and command. Evidence and reports are versioned and paired with local SHA-256 hashes. Hashes detect changes; they do not authenticate the collector or certify the cluster. The paired evidence JSON contains the data behind each JSON pointer.

        

        
Applying recommendations. A recommendation may not apply to every cluster. Confirm current platform support and workload requirements; document applicability, accepted deviations, and compensating controls in the relevant architecture or operations record.
